# JavaTracker

## Этап 13: Database Migrations (Flyway Integration)

На данном этапе в проект была интегрирована система миграции базы данных. 

---

### Два способа внедрения Flyway в Spring Boot

#### Способ 1: Декларативный (Автоконфигурация через `application.yml`)
Классический подход, заложенный создателями Spring Boot. 
Разработчик просто добавляет зависимости в `pom.xml`, а все параметры управления прописывает в конфигурационном файле.
*   **Как это работает:** Spring Boot при старте сканирует classpath. 
* Если он находит библиотеки Flyway и папку `db/migration`, фреймворк автоматически создает 
* бин `FlywayMigrationInitializer`. Этот бин принудительно встраивается в цепочку запуска **строго до** 
* инициализации Hibernate и автоматически накатывает скрипты.
*   **Плюсы:** Минимум кода (0 строк Java-кода), всё управление декларативно и наглядно 
* настраивается через свойства `spring.flyway.*`.

#### Способ 2: Программный (Силовой запуск через чистый Java-код)
Архитектурный подход, используемый в сложных корпоративных проектах для полного контроля над жизненным циклом приложения.
*   **Как это работает:** Разработчик полностью отказывается от автоконфигурации 
* Спринга и пишет изолированный утилитный класс (в нашем проекте — `DatabaseMigrator.java`), 
* внутри которого вручную настраивает конфигуратор `Flyway.configure()`. Метод `flyway.migrate()` 
* вызывается принудительно в методе `main()` главного класса приложения `DemoApplication.java`.
*   **Плюсы:** Абсолютная, 100% надежность. Позволяет организовать сложную кастомную обработку 
* ошибок через блоки `try-catch`, вести продвинутое логирование или динамически подставлять параметры DataSource 
* в зависимости от профиля окружения.

### Стек технологий проекта

#### Базовый стек:
*   **Java 17 / 21** — современный LTS-релиз с поддержкой Stream API и Concurrency.
*   **Spring Boot 3.x** — основа бэкенд-инфраструктуры приложения.

*   **Spring Security** — ограничение прав доступа (роли USER, ADMIN) и хеширование паролей через BCrypt.
*   **PostgreSQL 15** — целевая реляционная система управления базами данных.
*   **Docker & Docker Compose** — изоляция окружения (в контейнере приложение стабильно использует режим `update`,

*   **PostgreSQL Dialect SQL** — написание чистых, конфигурационных SQL-скриптов DDL/DML для физического развертывания таблиц.

### Что добавилось на данном этапе:

1.  **Strict Schema Validation (Жесткий контроль схемы):**
   *   В локальном профиле свойство `spring.jpa.hibernate.ddl-auto` переведено в бескомпромиссный режим `validate`. 
   * Hibernate полностью лишен прав на изменение таблиц и осуществляет только проверку соответствия сущностей структуре БД.
2.  **Baseline & Idempotency Strategy (Стратегия отсчета и идемпотентности):**
   *   Внедрены конфигурационные флаги `baseline-on-migrate: true` и `baseline-version: 0`. 
   * Это защищает живую локальную базу данных от падения, создавая служебную таблицу `flyway_schema_history` 
   * и принимая текущую точку за нулевую версию.
3.  **Отказоустойчивый SQL-скрипт (`V1__Init_DB.sql`):**
   *   Написан чистый SQL-скрипт, воссоздающий структуру таблиц `users`, `tasks` и `user_role` на уровне СУБД. 
   * Внедрен составной первичный ключ `PRIMARY KEY (user_id, roles)` для ElementCollection ролей и каскадное 
   * удаление `ON DELETE CASCADE` для связей Many-to-One.
4.  **Разделение окружений (Local vs Docker):**
   *   Для обеспечения гибкости учебного процесса логика разделена: локальный сервер управляется 
   * версионированием Flyway, а Docker-контейнер изолированно использует классический режим автообновления `update`, 
   * защищая контейнеризацию от Race Condition при старте.

### Проверка работоспособности кода

Для демонстрации работы механизмов по отдельности, архитектура легко переключается специальными "тумблерами" 
в коде и конфигурации. Перед каждой проверкой необходимо полностью очистить локальную базу данных через терминал `psql`:
```bash
\c postgres
DROP DATABASE IF EXISTS javarush_tracker;
CREATE DATABASE javarush_tracker;
```

#### Вариант А: Программный (Силовой автономный старт):
*   **Настройка**: В файле `application.yml` отключите автоматику Спринга: `spring.flyway.enabled: false`. 
* В классе `DemoApplication.java` раскомментируйте ручной вызов в методе 
* `main`: `DatabaseMigrator migrator = context.getBean(DatabaseMigrator.class); migrator.runMigration();`.
*   **Ожидаемый результат**: При старте приложения в консоли полетят кастомные логи: 
* `>>> СИЛОВОЙ АВТОНОМНЫЙ СТАРТ МИГРАЦИИ FLYWAY <<<`, а затем отчет о создании таблиц.
* Миграция выполняется строго один раз силами кастомного Java-движка.

#### Вариант Б: Декларативный (Стандартный автозапуск Spring Boot):
*   **Настройка**: В файле `application.yml` включите автозапуск: `spring.flyway.enabled: true`. 
* В классе `DemoApplication.java` закомментируйте ручные строчки вызова мигратора: `// migrator.runMigration();`.
*   **Ожидаемый результат**: Код метода `main` остается идеально чистым, 
* за всю миграцию «из коробки» отвечает автоматика Spring Boot. В логах отобразится стандартный отчет: 
* `Migrating schema "public" to version "1 - Init DB"`.

#### Универсальная проверка структуры СУБД (изнутри базы)
Зайдите в терминал `psql`, переключитесь на свою базу и проверьте результат физического развертывания:
```sql
\c javarush_tracker
\dt
```
*   **Ожидаемый результат команды `\dt`**: 
* Терминал выведет список из 4 созданных таблиц (`users`, `tasks`, `user_role`, `flyway_schema_history`).
```sql
SELECT * FROM flyway_schema_history;
```
*   **Ожидаемый результат запроса SELECT**: 
* Будет выведена строка с версией `1`, описанием `Init DB` и зафиксированной контрольной суммой 
* (checksum) файла миграции, подтверждающая свойство полной идемпотентности Flyway.
