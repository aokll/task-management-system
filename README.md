# Java Task Tracker (Stage 4: Service Layer Refactoring)

Четвертый этап разработки посвящен архитектурному совершенствованию проекта. Мы внедрили сервисный слой, 
разделив ответственность между компонентами системы.

## Новая архитектура (Service Layer)

На этом этапе мы отошли от прямого взаимодействия контроллеров с репозиторием и внедрили паттерн **Interface/Implementation**:

1.  **Controller Layer**: Теперь является "тонким". Он только принимает HTTP-запросы и делегирует выполнение бизнес-логики сервису.
2.  **Service Layer (`TaskService`)**: "Мозг" приложения. Здесь сосредоточена вся логика: расчет прогресса, фильтрация, проверка существования данных и обработка исключений.
3.  **Data Layer (`Repository`)**: Отвечает исключительно за сохранение и получение данных из PostgreSQL.

### Преимущества такого подхода:
*   **Слабая связность (Loose Coupling)**: Легко заменить логику работы, не меняя контроллеры.
*   **Инкапсуляция**: Контроллер не знает о деталях работы с базой данных.
*   **Удобство тестирования**: Возможность тестировать бизнес-логику отдельно от веб-слоя.

## Инструкция по управлению

### 1. Сборка и запуск
```bash
# Сборка проекта
mvn clean package

# Запуск в Docker (с пересборкой сервисного слоя)
docker-compose up --build
```

### 2. Проверка архитектурных изменений
При запуске убедитесь, что все операции (добавление, удаление, поиск) проходят через `TaskServiceImpl`. В логах контейнера `java_app` теперь можно отследить цепочку вызовов.

---

## Ключевые эндпоинты (API)

*   `GET /api/tasks/all` — Получение списка всех задач через сервис.
*   `GET /api/tasks/delete?id=...` — Удаление задачи с предварительной проверкой в сервисе.
*   `GET /api/tasks/search-by-title?title=...` — Поиск с игнорированием регистра.
*   `GET /api/tasks/sort-by-topic-and-status` — Сложная фильтрация через бизнес-логику сервиса.
